# Core Hub — iOS

The native SwiftUI client of [Core Hub](https://github.com/twuijri/core-hub) (twuijri's fork of Hermes Studio). It talks to the same `/api/studio/*` REST routes and Socket.IO namespaces as the web client and keeps the bearer token in the iOS Keychain.

The version follows the core (`package.json` at the repository root); see `docs/mobile/PLAN.md`.

## Design system (M2)

`HermesStudio/Theme/CoreHubTokens.swift` is the single source of the "Pure Ink" design system from `docs/mobile/DESIGN-SPEC.md`:

- `CoreHubTokens.PaletteHex.light/.dark` — the raw hex values (unit-tested); `CoreHubTokens.Palette.*` — dynamic `Color`s that follow the effective colour scheme (system, or the user's light/dark choice through `preferredColorScheme`). State formulas: `hover` = accent @ 6 %, `selected` = accent @ 12 %, `inputBorderIdle` = accent @ 18 %.
- `Typography` (14 base; 16/600 titles; 13 nav/session; 12 author; 11 meta; 10/600 uppercase group headers; monospaced code; inputs never below 16 pt), `Radius` (6/8/10/14/18/999/4/5), `Shadow` (card, composer light/dark, focused), `Motion` (150/250 ms), `Layout` (sidebar 240, header 60, drawer ≤ 300, …).
- The app tint is `Palette.accent`; every view touched in M2 uses tokens only.

Icons: `Theme/IconPath.swift` parses the 24-viewBox SVG path data written in the spec (`M/m L/l H/h V/v C/c A/a Z` plus circles and rounded rects; arcs become cubic curves) and `Theme/CoreHubIcons.swift` lists the rail, segment and header icons drawn with stroke 1.8 and round caps. Directional icons (`chevronForward`, `back`, `chat`, `workflow`, `history`) mirror in RTL. `CoreHubMarkView` draws the vector Core Hub mark.

Agent avatars: `Theme/AgentAvatar.swift` maps a session's runtime id to the bundled assets `Agent-*` (copied from `packages/client/public/coding-agents/`; SVGs are used as vector imagesets, large PNGs were downscaled to 256 px) exactly like the web's `chat-agent-avatar.ts`. Those are the *runtime* logos and are unrelated to the profile avatars below.

Profile avatars: `Theme/BoringAvatar.swift` is a Swift port of `boring-avatars-vanilla` (MIT), the generator behind the web's `components/hermes/profiles/ProfileAvatar.vue` — the `beam` variant with the library's default palette, seeded exactly as the web seeds it (`avatar.seed` → the display name → `default`). The port is literal, not an approximation: `hashCode` walks **UTF-16 code units** (an emoji contributes two), the intermediate arithmetic wraps at 32 bits, `Math.abs(Int32.min)` widens to 2 147 483 648, and `getUnit`'s `index` argument is skipped when it is `0` because JavaScript treats `0` as falsy. `BeamAvatarView` draws the result with `Canvas` in the library's own 36 × 36 user space — including the SVG clamping rules the markup relies on (`rx="36"` on a 36-wide rect is a circle; the eyes' `rx="1"` on a 1.5 × 2 rect is a full ellipse; the closed mouth's `a1,0.75` radii are scaled up to 5 × 3.75 for the 10-unit chord) — so nothing ships an SVG renderer. `ProfileAvatar` in `Theme/HermesTheme.swift` still prefers a stored `avatar.type == "image"` data URL, cached as a bitmap by `AvatarImageCache`; only image avatars touch that cache now. The old cartoon `multiavatar.json` generator, its licence file and the WebKit SVG-snapshot renderer that rasterised it are gone — nothing referenced them any more. `HermesStudioTests/BoringAvatarTests.swift` pins the port against 17 seeds whose expectations were read out of the SVG the web library itself returned (Latin, Arabic, an emoji, an empty seed and the library's own `Clara Barton` default).

## Navigation (M2, unified 2026-09-20)

The navigation is the contract in `docs/mobile/NAVIGATION.md`, derived from the desktop client (`packages/client/src`); Android implements the same map, and the desktop is the reference wherever the contract is silent.

**The registry.** `Core/NavDestination.swift` — `enum NavDestination: String, CaseIterable` with 36 cases (`newChat, search, deviceConnections, agentManager, models, chat, groupChat, workflow, history, settings, logs, usage, performance, skillsUsage, theme, pets, profiles, conversation, room, workflowDetail, workflowRun, agentHermes, agentEkko, agentCoding, jobs, kanban, channels, skills, plugins, mcp, memory, journey, hermesSettings, ekkoSettings, codingAgentSettings, globalAgent, files`). Each has `labelKey = nav_<snake_case>` present in `en.lproj` and `ar.lproj` with the contract's terms; the entry that opens a screen and the screen's title read the **same** key. `ConversationMode` is a projection of the four segment cases.

**The stack.** `Features/RootShell.swift` holds one `NavigationStack(path: $store.path)` (`NavigationPath`) with one `navigationDestination(for: NavDestination.self)`; `ShellDestinationView` is an exhaustive `switch` over the registry. `store.show(_:)` replaces the pushed stack (a rail entry, the gear) and `store.push(_:)` nests, so Agent Manager → Hermes → Kanban → task is a plain push, like the desktop. Destinations with a payload (`conversation`, `room`, `workflowDetail`, `workflowRun`, the three `agent*` cases, and the per-agent `skills`/`plugins`/`mcp`/`memory`/`*Settings`) resolve against the store (`selectedSession`, `selectedRoom`, `selectedWorkflow`, `selectedWorkflowRunID`, `focusedAgentID`). One rule keeps the value links working (header of `RootShell.swift`): a `NavigationStack(path:)` honours `NavigationLink(value:)` only from a screen that is itself in the path, so a screen that contains value links is never pushed by a view-destination link (`NavigationLink { … }`) — the Agent Manager cards call `store.openAgent`, `AgentDetailView` is built by `AgentScreenLoader` alone, and `NavigationRulesTests` reads the sources to keep it that way. TestFlight build 41 broke this: the card was a view-destination link, so the Hermes rows (Jobs, Kanban, …) appended to a path that did not contain the screen they were on, and nothing opened.

**The drawer** (`Features/SidebarDrawer.swift`, 250 ms slide, 40 % scrim, swipe to close, edge swipe to open):

## Chat (M3)

`Features/ConversationView.swift` owns one conversation; everything below it lives in `Features/Chat/`.

- **Socket.** `Core/SocketIO.swift` keeps one `/chat-run` connection open for the whole conversation (`auth: { token }`, `query: { profile, platform: 'ios' }` — the platform registers the phone as a mobile device target), emits `app.resume` on every connect, reconnects with exponential backoff (≤ 30 s) and immediately when the app returns to the foreground. `ChatSocket.events(for:json:sessionID:)` is the pure server→client mapping (`message.delta/interim`, `reasoning.*`, `tool.started/completed/failed` with truncation flags, `subagent.*`, `run.*`, `approval.*`, `clarify.*`, `compression.*`, `abort.*`, `usage.updated`, `session.command`, `session.title/workspace/settings.updated`, `resumed`, `location.requested`, `calendar/reminder/health.requested`). Client→server: `run`, `abort`, `approval.respond`, `clarify.respond`, `insert/steer/cancel_queued_run`, `location.respond`; calendar/reminder/health requests are answered `denied` for now.
- **State.** `Core/ChatStream.swift` — `ChatStreamState` and the pure `ChatRunReducer` (lines of kind user/assistant/system/command/error/interaction, interim text, thinking timestamps, tool upserts, queue, compression, abort, peer messages, settings, location), plus `ToolSummary`, `ThinkingFormat`, `ReferenceQuote`, `ContextUsageFormat` and `ReasoningEffortOption`. All unit-tested in `HermesStudioTests/ChatParityTests.swift`.
- **Rows.** `MessageRow.swift` (user ≤ 75 %, assistant with 22 pt agent avatar ≤ 80 %, system with a 3 pt warning border, command, error, streaming dots, attachment chips), `ToolSummaryCard.swift` (30 pt header, chevron, wrench, "N tools", ≤ 3 names + N, ✓/•••/Error; 11 pt mono lines with Thinking/Arguments/Result), `ThinkingBlock.swift` (💭 Thinking · Observed {duration} · {count} chars), `MessageActionRow.swift` (speech play/pause, copy, reference, fork, time), `InteractionCard.swift` (approval choices / clarification answer inline in the stream), `ChatBanners.swift` (queued runs, compression, abort, reconnecting, workspace changes).
- **Composer.** One composer serves both the conversation and a group room. `Shared/ComposerCard.swift` draws it — radius-18 card, min 150 pt, reference chip, attachment strip with progress and cancel, the dictation status row, a 16 pt input with per-string direction (never auto-focused), the toolbar [+ attach] [pills…] … [queue] [mic 30] [send / stop 30], and the counter in the top end corner. Labels collapse to icons under 380 pt. `Shared/ComposerControls.swift` holds the individual controls, so a fix to the microphone or to a chip is a fix on both screens. While the microphone is open the toolbar gives way to the **recording strip** (`Shared/RecordingStrip.swift`, see *Voice input*): [✕ cancel] [live waveform] [■ stop] [↑ send].
- **What each screen asks for.** `Shared/ComposerModel.swift` — a `ComposerConfiguration` (placeholder, pills, ⚙ rows, trailing controls, counter, whether send turns into stop) plus the shared `ComposerState` / `ComposerActions`. `ChatComposer.swift` and `GroupChat/RoomComposer.swift` are thin wrappers around `.chat` and `.room`. A pill is listed only when the screen honours it, never as decoration; `ComposerParityTests` pins both configurations.
  - **chat**: [🧠 reasoning] [⚙ Voice mode · Show tool calls · Push] [model ≤ 190 pt] … [queue while a run streams] [mic] [send / stop]; counter = the context indicator ("45.0k / 256.0k · remaining 211.0k", amber above 80 %).
  - **room**: [@ Mention] [⚙ Show tool calls] … [mic] [send]; counter = the room's token total with no bar. Left out on purpose: the **model** and the **reasoning effort** (a session owns them, and every seat carries its own model — both live in the room settings), **Voice mode** and **Push** (a room has no TTS path and no push flag), **queue** (a chat socket call), and **send-as-stop** (several seats can be replying, so each is interrupted from the room's activity strip). Nothing else differs.
- **Attachments.** `Core/AppUploads.swift`: chunked `/api/studio/app-uploads` (client id, ≤ 256 KiB raw chunks, complete → `{ name, path }` used in the content block, DELETE on cancel, 50 MB cap). Pickers in `AttachmentPickers.swift`. The "+" opens the attachment sheet (`Features/Chat/AttachmentSheet.swift`), not a pop-up menu: a bottom sheet with a 36 × 4 drag handle, the title "Attach files" (the web's own label) over a muted line, then PHOTOS — *Take photo* · *Photo library* — a divider, DOCUMENTS — *Files* — and a full-width *Close*. Each row is one line: a 40 pt icon tile (the 24-viewBox camera, image and paperclip icons at stroke 1.8, on accent @ 6 % with a border-light hairline, radius 10), the 14/600 label over an 11 pt caption, and a chevron that mirrors in Arabic. Detents: a token-computed height plus `.large`; corner radius 18, `bg.card` background. The picker is launched from the sheet's `onDismiss`, so the camera never opens behind a closing sheet. Android's `AttachmentSheet.kt` carries the same rows, order, icon paths and wording — `AttachmentSheetTests` and Android's `AttachmentSheetTest` keep the two in step.
- **Media.** `Core/MediaLinks.swift` + `MediaPlayers.swift`: absolute paths and `device://<id>/<path>` links stream from `/api/studio/files/download?path=…` with the bearer header (`AVURLAsset` + `AVURLAssetHTTPHeaderFieldsKey`); video (mp4/webm/mov/m4v) and audio (mp3/wav/ogg/m4a/aac/flac) play inline, other files are download cards, device files carry the "On the device" badge.
- **Speech.** `Core/MessageSpeaker.swift`: per-message play/pause of the synthesized reply, optional auto-play (Voice mode), and the `AVSpeechSynthesizer` fallback. Which voice speaks, and how the request is built, is in "Spoken replies" below.
- **Consent.** `LocationConsentSheet.swift` + `Core/LocationConsent.swift`: `location.requested` → sheet with the purpose → one CoreLocation fix → `location.respond` (`success` with WGS-84 coordinates, `denied`, or `error`). Requires `NSLocationWhenInUseUsageDescription`.

## Sessions, group chat, workflows and settings (M4)

**Sessions.** Search across titles and message text with snippets (`GET /api/studio/sessions/search`), the archived list from the History groups endpoint with Unarchive, an "All profiles" filter shared by the drawer and History, batch mode (archive / unarchive / delete / move to category), category ⋯ menus, export through the share sheet, session settings (model, reasoning effort, push, workspace, category, usage, current context) and paginated history with "load earlier" (`/messages/paginated`). Pure helpers: `SessionBatchSelection`, `MessagePaging`, `BatchResult`, `SaveState`.

**Group chat** (`Features/GroupChat/`, models and transport in `Core/GroupChat*.swift`).

- **REST.** `Core/GroupChatAPI.swift` covers rooms (list, detail with paging, create, clone, delete), `config` / `workspace` / `invite-code`, the agent seats, members, `clear-context`, the room summary, the handoff chains, `rooms/join/{code}`, the agent presets and both attachment routes (multipart and the chunked `attachment-uploads`).
- **Socket.** `Core/GroupChatSocket.swift` keeps one `/group-chat` connection per room: `auth: { token }`, an acknowledged `join` on every (re)connect, exponential backoff, and the pure `GroupRoomSocket.events(for:json:roomID:)` mapping (`message`, `message_stream_start/delta/end`, `message_reasoning_delta`, `member_joined/left/kicked/updated`, `agents_updated`, `typing`/`stop_typing`, `room_agent_activity`, `execution_queue_updated`, `message_retracted`, `room_summary_updated`, `handoff_updated`, `approval.*`, `clarify.*`, `room_updated`, `room_cleared`, `context_status`). Sending uses the acknowledged `message`, `interrupt_agent`, `cancel_execution_queue_item`, `approval.respond`, `clarify.respond` and `load_messages`. Structured `mentions` are deliberately **not** sent: the server resolves @mentions from the text for human senders and rejects metadata that does not match exactly, so the @ menu only inserts text.
- **State.** `Core/GroupChatStream.swift` — `GroupRoomState` + the pure `GroupRoomReducer`, and `GroupRunLines`, which folds every message of one agent run (assistant + `tool` messages sharing a `run_id`) into one M3 `ChatLine` so the room reuses the message row, the tool card and the thinking block.
- **Screens.** `GroupRoomsView` (rooms with agent avatars and member counts, create, join by code, rename, duplicate, delete), `GroupRoomView` (transcript, per-agent activity with interrupt, typing, execution queue, inline approvals/clarifications, stopped handoff chains with Continue, "load earlier", the shared composer with dictation, the attachment sheet, the @ menu and the chunked room upload), `RoomSettingsView` (name, summary policy and handoff depth, workspace, invite code with the CoreImage QR and share link, seats with preset CRUD, members, clear context, summary) and `RoomAgentEditorView`.

**Workflows** (`Features/Workflow/`). The list carries live status chips from the `/workflow` socket (`WorkflowLiveStatuses` owns the acknowledged `workflows.list` and `workflow.status.subscribe`), plus create, import (preview → confirm → cancel) and delete. The workflow screen runs (optional input, start nodes, timeout), stops, lists the runs and links to the schedules and the read-only graph summary. The run screen merges the persisted node sessions with the live `nodeStatuses` (`WorkflowGraph.timeline`), shows status, duration and errors, offers the inline approval on blocked nodes, loads a node's output from its session, and can rerun from a node. Schedules show a human cron description (`CronDescription`) with an enable/disable switch. Graphs are never edited on the phone.

**Settings.** See "Navigation" above for the unified layout. Every control shows Saving / Saved or the server error (`SaveButton`, `SaveStateLabel`).

Every Studio request now carries `X-Hermes-Profile`: `APIClient.activeProfile` is the default header and `AppStore` keeps it in step with the selected profile.

## Models and Agents (M5)

Two screens were rebuilt because they did not show what Core Hub itself shows.

**Models** (`Features/Models/ModelsHomeView.swift`) now mirrors `views/hermes/ModelsView.vue` → `ProvidersPanel.vue` → `ProviderCard.vue`: the **service providers this profile has credentials for**, and under each one **the models it offers**. Each provider is a section — name, the Default / Built in / Custom badges and the key dot in the header, the pool key, base URL and OpenCode-free catalogue status in the footer — holding a "Models N" disclosure (or `N/total` once a visibility rule hides some, the web's `visibleCountLabel`) and a *Provider settings* link. Tapping a model makes it the default for that provider (`PUT /api/hermes/config/model`), the way the web card's default-model select does; ⋯ opens the alias and context-limit sheet. The screen also carries *Refresh model cache*, *Add a provider* and *Provider sign-in*, and an empty state instead of a blank list.

What it no longer does is open on key management. Credentials, the visibility rule, custom models, the connection test, *Refresh models* and *Restore the model list* moved one level down into `ProviderCatalogView`, which is where the web hides them too, and the destructive action now says what it actually does — *Delete this provider* for a config-backed pool, *Clear the stored key* for a built-in one (the web's `isConfigBackedProvider` split). The drawer's Models rail item and Settings → Models both land here; the old flat model picker and the duplicate provider-status list are gone, and `ProviderSignInView` keeps only the browser sign-in flows (Codex, Nous, xAI, Anthropic) that the web puts in its login modals.

A decoding bug went with it: `ModelCatalog` used to merge `groups` **and** `allProviders`, so the phone listed every provider Core Hub has ever heard of rather than the ones this profile is configured for. `allProviders` is now kept apart as `presets` and consulted only to widen a provider whose own `available_models` is empty, exactly like `ProviderCard`'s `sourceProvider` fallback; the virtual `moa` routing provider is filtered out as in the web store.

**Agents** (`Features/Agents/`) renders the server's inventory instead of a hardcoded list. `GET /api/agents/status` returns all eight agents in its own order — `hermes`, `ekko-agent`, `claude-code`, `codex`, `pi`, `grok`, `opencode`, `dsh` — and the screen groups them by the registry's own `kind` (`built-in` / `hermes` / `coding-agent`), with an "Other agents" section for a `kind` this build does not know. The previous screen listed five agents it had written down itself, and `AgentIdentity.canonicalID` collapsed `grok`, `opencode` and `dsh` into `hermes` on the way in; both are fixed, and `AgentRuntimeStatus` now keeps the server's id verbatim so a future agent appears with a readable name rather than being folded into another row. `/api/agents/status` needs super-admin: when it is refused the six coding agents still come from `/api/coding-agents` and the screen says the rest needs a super-admin sign-in rather than presenting a short list as complete. Refresh replicates the web's order — `GET /api/coding-agents` and `GET /api/hermes/runtime-versions?remote=false` first, because the status registry is only populated as a side effect of those probes, then re-read the inventory.

Every agent now **opens**, and the list is drawn like the Android `AgentManagerScreen.kt` — the design the owner chose after comparing the two phones ("شكل الأجنتات بالأندرويد أجمل"). `AgentManagerView` is a scroll of cards (`AgentCardView`, chrome in `AgentCardViews.swift`) 10 apart inside 16 × 8/28: an intro line, the info-tinted "runs on the server" note, then `Hermes runtime` · `Built in` · `Coding agents` (Android's `AgentKind` order) under 13-bold headers. A card is bg.card at radius 18 with a 1 pt border and 16 of padding, lines 8 apart: a 34 pt avatar 12 from the name (14 bold) over the vendor (12), the state pill (11 semibold on its colour @ 16 %, 10 × 5) with the compact `Update` pill under it (`AgentUpdateButton`, info @ 16 %, 12 × 5, label only so it never wraps) at the trailing edge; the meta line `Local CLI · vX · vY available`; the package and the path in 11 mono; the error in `error`; the `Update automatically` switch (`PUT …/update-policy`, only when `autoUpdateSupported`); and the actions row (`AgentActionsFlow`, 6 apart, wrapping from the start edge in both directions): `Agent settings` as a 40 pt outlined pill with the 16 pt gear, then the text buttons `CLI details` (Hermes on a local CLI; an alert with version, path and error), `Reinstall` / `Install`, `Check for an update` and `Delete` (a confirmation, then `DELETE /api/coding-agents/{id}`). Install, update, check and remove therefore run from the card, as on Android; `AgentDetailView` keeps the CLI details, the capabilities and Settings. Every number is a `CoreHubTokens` entry (`agentCard*`, `agentRow*`, `settingsRow*`, `tabRow*`, `loadingRow*`), and `AgentManagerParityTests` reads the Kotlin so the two phones cannot drift again. Install and remove run `npm -g` on the **server** and block for up to ten minutes, so `APIClient` grew a per-request timeout (`codingAgentInstallTimeout`, 11 minutes) — the 60 s session default gave up long before the server did — and a failed npm run answers HTTP 200 with `success: false`, so the flag is reported, not the status code. Below that sit the two files the web's agent settings page edits (`GET`/`PUT /api/coding-agents/{id}/config-files/{key}`, keyed per agent exactly like `CodingAgentConfigView.vue`: `memory`/`settings` for Claude Code, `agents`/`config` for Codex, `agents`/`settings` for Pi and Grok, `memory`/`settings` for OpenCode and DSH) and the agent's MCP servers (list, test, remove; adding one needs its JSON config and says so).

Each agent's screen lists its capabilities and its settings in the desktop sidebar order (see "Navigation"); `AgentDetailView` is the only parent of those screens.

One of them did not exist at all. `Features/Agents/HermesMemoryView.swift` is the phone's `views/hermes/MemoryView.vue`: the profile's three Markdown files — My Notes, User Profile and Soul — through `GET`/`POST /api/hermes/memory`, with the server's `§` paragraph separator expanded back to blank lines the way the web does before rendering. It is Hermes → `Memory`; the memory **settings** are the `Memory` tab of Hermes → `Settings`. Ekko memory (`/api/ekko/memory`) is Ekko → `Memory`.

Still missing on the phone, on purpose: the web's runtime download/activate drawer (`VersionManagementModal`) and the runtime versions screen altogether (the runtime ships in the server image; the installer belongs to the desktop app), the "Ask AI" diagnose flow after a failed install, installing DSH web packages and the DSH plugin UI session (the inventory is shown; the presets screen lists the roster, makes one the default and deletes a user copy, while copying a preset and editing its file stay on the desktop, as its footer says), editing the reference models of a model ensemble, entering voice-provider keys (the phone picks the active STT/TTS provider), and adding or editing an MCP server. Nothing on either screen runs on the iPhone — an install is `npm install -g` on the Core Hub host, a config file is a file in the server's home directory — and the detail screen says so.

## Connecting to Core Hub (M1)

- **QR pairing (recommended).** In Core Hub open *Settings → App connections → Create LAN pairing code* and scan it with **Scan QR code** on the login screen. The app calls `POST /api/auth/app-login` with a stable `device_code` (a UUID generated once and kept in the Keychain), the editable device name, `device_brand: Apple` and the hardware model. The token, its expiry and the connection id are stored together as one Keychain item.
- **Silent refresh.** `POST /api/auth/app-refresh` runs on launch when fewer than 7 days remain or the last refresh is older than 24 h, and once after any 401 (the failed request is retried with the new token). A 401 from the refresh itself signs the device out with a message. Decision logic: `AppTokenRefreshPolicy` (unit-tested).
- **Username/password** sign-in remains available under *Sign in with username and password*.
- **Canonical routes.** Sessions, messages, search, categories, usage, performance, group chat, files, STT, TTS and the REST chat-run endpoint use `/api/studio/*`. Profiles, config, models, skills, plugins, MCP, Kanban and jobs stay under `/api/hermes/*`. Bearer tokens are sent only in the `Authorization` header — never in a URL query — so downloads (agent files, workspace files, Kanban attachments) are fetched with `URLSession` and opened from a local copy.

## Voice input (M1)

- **Default: this device.** Apple Speech (`SFSpeechRecognizer` + `AVAudioEngine`) with partial results; the words appear live in the composer and the final text stays there. Nothing is sent automatically. **A take lasts until you end it.** Apple ends a recognition request on its own — after about a minute of audio when its server does the recognition, and at times after a long pause ("no speech detected") — with a final result or an error; none of that ends the take. `DictationTake` (pure, `Core/Dictation.swift`) commits the ended request's text with `DictationText.merged`'s separator rules, and `OnDeviceSpeechRecognizer` opens the next request on the **same** audio engine and tap (`SpeechRequestFeed` swaps the request under a lock, the new one before the old one's `endAudio()`, so no buffer is lost and the waveform never drops); the next partials land after the committed text and the strip and the "Listening…" row stay put. ↑ during that gap sends what is in the field — the committed text plus the in-flight partial. Restarting stops only on ■ / ↑ / ✕, on a real failure (permission gone, recogniser unavailable, audio engine stopped by an interruption, or three requests in a row dying with nothing heard in under two seconds — no network for Apple's server), or at the ten-minute ceiling, where the take ends as ■ would and a notice says so. A callback from a superseded request is dropped by generation. The server path (`VoiceRecorder`, one WAV per take) is untouched.
- **Option: Core Hub server** (*Settings → This device → Voice input*). The app checks `GET /api/studio/stt/profile-status` first and explains any `reason`, records 16 kHz mono 16-bit PCM WAV, and posts it to `POST /api/studio/stt/transcribe` as multipart (`provider`, optional `language`, file part `audio` = `voice.wav`). `no_speech_detected` and every other failure are shown in the banner.
- When on-device recognition is unavailable or its permission is denied, the app falls back to the server path for that attempt; when the server cannot transcribe, it falls back to the device with a banner naming the language it used. Neither direction is silent.
- Mic button states: idle → listening → transcribing → error.

### Recording strip

Tapping the mic swaps the composer's pill row for a recording strip modelled on the Claude app's, on both screens and in both interface directions: a round **✕** at the leading edge, a live **waveform** filling the middle, a round **■** and the accent **↑** at the trailing edge — the same 30 pt round controls the composer already uses (`bgCard` for ✕ and ■, `accent` for ↑). The swap runs on `Motion.drawer` (250 ms) and simply cuts when Reduce Motion is on. The transcript keeps landing in the field above, which stays editable; the "Listening… / language" status row stays where it was, minus its "tap the microphone" tip, since the mic is off screen while listening.

- **✕ cancels**: recognition stops without waiting for a final result and the draft that existed before the take comes back exactly — with whatever trailing space or newline it had, because `DictationText.merged` only ever appends after `DictationState.base`. **■ stops**: the take ends, the text stays, the pill row returns (the mic shows "transcribing" until the final result lands on the device path, or the WAV goes up on the server path). **↑ while recording** stops and sends what is in the field. The language long press lives on the mic, which is only there when not recording.
- **Levels are real.** `Core/AudioLevel.swift`: `AudioLevelTap` reads each buffer inside the tap `OnDeviceSpeechRecognizer` already installs on the `AVAudioEngine` input (one tap, two readers: the recogniser gets the buffer, the strip gets its RMS) and publishes a normalised level about 20 times a second; the server path reads `AVAudioRecorder`'s own metering on the same cadence. No second audio session. `AudioLevelMeter` gives RMS → dBFS, and the strip's window **follows the signal** (`AudioLevelRange`): the recogniser's session runs in `.measurement` mode, which turns the system's input processing (automatic gain) off, so the raw microphone sits far below the −50…−10 dBFS window that suits a processed input — a quiet room near −70, speech at arm's length near −45 — and with a fixed window the strip showed a sliver at best and mostly dots (TestFlight build 48: only idle dots while speaking). Now the floor is the quietest level of the last two seconds, the peak follows the loudest and falls at 3 dB/s, a level within 6 dB of the floor is a dot and the peak sits at least 12 dB above the floor, so room noise never draws and the first word fills the strip whatever the gain. Bars keep the instant attack and exponential release (about 10 % left after half a second). The server-path recorder's `averagePower` is a processed input and still uses the fixed −50…−10 window. `RecordingWaveform` is the last 36 levels, newest last, scrolling; it lives on the recogniser/recorder as `@Published` and reaches the card through `ComposerState.waveform`, so the view holds no timer.
- **Drawing.** `RecordingWaveformView` is one `Canvas`: 36 bars of `accent` across the free width (`Layout.waveformBarCount/BarGap/Dot`), a bar with sound at full alpha, an idle bar collapsed to a 3 pt dot at `Alpha.waveformIdle` (40 %). A time line reads oldest-left everywhere, so the waveform pins its own layout direction while the strip around it mirrors with the interface (✕ stays at the leading edge in Arabic).
- **VoiceOver** gets the same three controls ("Cancel dictation" / "Stop dictation" / "Send", each with a hint) and the waveform as one element labelled with the dictation language ("Recording in العربية …") whose value is the current level in percent.
- The rules are `RecordingStrip` in `Core/Dictation.swift` (visible only while `.listening`; cancel → base, stop → current and await the final result, send → current and send), applied by `DictationRunner.cancel()` / `stop()` / `endForSend()`. `RecordingStripTests` pins the arithmetic and the rules.

### Dictation language

`Core/SpeechLanguage.swift` owns this; the views have no logic.

The app language is **not** the dictation language — an English phone running an English app is a normal way to speak Arabic, and following the UI was why the mic returned English words for Arabic speech. The default now follows the **keyboards the owner actually types with**: `UITextInputMode.activeInputModes` (public UIKit, no permission) gives each enabled keyboard's `primaryLanguage`, and the first one Apple Speech supports wins — preferring a keyboard that is *not* the app language when more than one is enabled, then the app language, then the device locale. `emoji` and `dictation` are input modes too and are dropped. The list is read at dictation time, not cached, because a keyboard can be added at any moment.

*Settings → Voice → Dictation language* (`Features/Settings/SpeechInputLanguageView.swift`) offers, per profile:

- **Follow my keyboard languages** — the default described above, on device.
- **Follow the app language** — `ar-SA` / `en-US` / the device locale, the behaviour before this preference existed, on device.
- **A specific language** — every locale in `SFSpeechRecognizer.supportedLocales()`, named by its own endonym (`العربية (المملكة العربية السعودية)`, not "Arabic"), Arabic first, then English, then the rest by name. A locale the recogniser does not support is never offered, and a stored one that stops being supported falls back to the keyboard default instead of pinning dictation to something that cannot run.
- **Let the Core Hub server detect it** — the only choice that leaves the device. Apple's recogniser takes one concrete locale and cannot detect across languages, so this records WAV and posts it to `/api/studio/stt/transcribe` with **no** `language` field. It is labelled as such in the picker and on the recording strip, is never a default, and is never entered by fallback.

The pick is stored per profile on the device (`Preferences.speechLanguage(for:)`: empty = keyboards, `app`, `server`, or a BCP-47 identifier) and reaches **both** paths — the recogniser's locale and the server's optional `language` hint (`ar-SA` → `ar`). The last three languages picked are remembered per profile (`Preferences.recentSpeechLanguages(for:)`) and shown in a "Recent" section.

Dictation itself is one implementation (`Core/Dictation.swift`: `DictationState`, the pure `DictationText.merged(base:transcript:)`, and `DictationRunner`, which holds no state and takes the screen's bindings). Both the conversation and a group room run that exact code, so the on-device/server decision, every fallback, the language long press, the hint policy and the way a transcript lands in the field are the same in both. A room resolves the profile the same way its rows do (the room's summary profile, else the selected profile).

**Long-press the mic** in the composer to open the same list as a sheet, so one Arabic dictation costs a gesture instead of a trip through Settings; the recording strip shows the language currently listening (or "Core Hub server"), so a wrong language is visible before the transcript comes back wrong.

A long press is invisible, so the app says it out loud — occasionally. The moment a recording starts, a transient one-line hint ("Touch and hold the microphone to change the dictation language" / "اضغط مطوّلًا على الميكروفون لتغيير لغة الإملاء") fades in **above** the composer: a pill on the composer's own tokens (11 pt meta, radius 999, `bgCard` on `borderLight`, card shadow, 250 ms `Motion.drawer`), never a modal, never focus-stealing, gone after five seconds, and tappable as a shortcut to the same picker. `DictationHintPolicy` in `Core/SpeechLanguage.swift` decides *when*: every one of the first three recordings, then recordings 8, 15, 22 … (a gap of five, then seven), and **never again** once the long press has actually been used. Both counters are per profile on the device (`Preferences.dictationCount(for:)`, `Preferences.dictationLongPressUsed(for:)`); only recordings that really opened the microphone are counted, so a failed start does not burn a hint or stack a tip on top of an error banner.

Note on the keyboard-derived default: `UITextInputMode.activeInputModes` lists every **enabled** keyboard, not the one currently on screen — iOS exposes no public API for the latter. Switching the iPhone keyboard to English therefore does not change dictation while an Arabic keyboard is still enabled: the resolver keeps preferring the keyboard that is *not* the app language. That is the intended behaviour of "Follow my keyboard languages" (it is what makes Arabic dictation work in an English app without any setup), not a bug. Pinning a language regardless of keyboards is the "A specific language" choice, one long press away.

Server-side caveat, verified in `packages/server/src/modules/studio/controllers/stt.ts`: the transcribe controller does **not** read the multipart `language` field — every provider takes its language from the profile's stored STT settings (`input.settings.language`). The hint is sent for forward compatibility and matches what the web client does, but today the server ignores it, so "let the server detect it" really means "whatever the profile's STT provider does with no language pinned in Studio → Voice". Fixing that is a server change and is out of scope here.

Required Info.plist strings: `NSCameraUsageDescription`, `NSMicrophoneUsageDescription`, `NSSpeechRecognitionUsageDescription`, `NSPhotoLibraryUsageDescription`, `NSLocationWhenInUseUsageDescription`. `ITSAppUsesNonExemptEncryption` is `false` (the app only uses the system HTTPS stack), so TestFlight no longer asks about export compliance on every upload.

## Spoken replies

The chat "speak" button uses the **profile's Core Hub voice**, exactly like the web client. `Core/VoiceOutput.swift` loads `GET /api/studio/tts/settings` (`settings` + `activeProvider`) per profile and `POST /api/studio/tts/synthesize` then carries `provider` plus that provider's stored options (`voice`, `model`, `rate`, …). The API key never leaves the server — the settings endpoint only reports that one exists (`[stored]`) — and `baseUrlPresets` is a UI history list, so neither is echoed back; empty values are dropped because the server's `mergeStoredTtsOptions` treats a present-but-empty option as an override. The response's `X-TTS-Provider` / `X-TTS-Engine` say what actually ran.

Sending no `provider` was the bug: the server then resolves one itself and falls back to `edge` (Microsoft's free voice) whenever the profile has no stored active provider, so the phone spoke in a different voice than the browser.

*Settings → Voice → Spoken replies* (`Features/Settings/VoiceOutputSettingsView.swift`) lists the providers configured for the active profile with the server's active one marked, plus this iPhone's built-in voice. The pick is stored per profile on the device (`Preferences.ttsVoice(for:)`); nothing stored means "follow the profile", which is the default. Picking a **server** provider also writes `PUT /api/studio/tts/settings/active`, and only when it differs from what the server already has; picking the device voice never writes anything to the server. On-device speech stays the default for voice **input** (M1 decision); this setting is only about the spoken reply.

Failures are named, not swallowed: `TtsFailure` carries the provider, the HTTP status and the server's `{ error, detail }` text, a JSON body returned with HTTP 200 is detected before it reaches `AVAudioPlayer`, and only then does the device voice take over — with a banner saying which provider failed and why.

## Arabic / RTL

`environment(\.layoutDirection)` follows the app language — that is the *interface* direction, and it is never the content direction. `Shared/ContentDirection.swift` is the iOS half of `docs/CONTENT-DIRECTION.md` and the single implementation of the rule:

- `ContentDirection.resolve(_:interface:)` — the browser's `dir="auto"`: the **first strong** character decides, and a string with no strong character at all (empty field, `2026-09-19`, `45.0k / 256.0k`, an emoji) keeps the surrounding interface direction. There is no "dominant language" guess: `Xcode لا يعمل…` is left-to-right and `شغّل npm run build` is right-to-left. Only letters are strong — the general category is checked directly, because `CharacterSet.letters` is L\* **and M\***, which used to make a bare Arabic diacritic (and a leading U+FEFF byte-order mark, which falls inside the Arabic presentation-forms range) read as strong right-to-left.
- `.contentDirection(of:)` — the counterpart of the web's `contentInputProps`, for text fields and text views. It must be the **last** modifier on the field: `frame(alignment:)` and directional padding resolve `.leading` against the direction of their own parent, so wrapping them is what puts Arabic at the physical right edge instead of leaving a right-to-left run inside a box still anchored left.
- `.technicalDirection()` / `TechnicalText` — code, paths, model ids, cron expressions, invite codes and the context counter are always LTR.
- `DirectionalText` for one-line content (session and room titles, agent names, snippets), `MarkdownText` for messages (per block, so an RTL paragraph can be followed by an LTR code block; the container stays physically LTR and each line opts in).

Covered surfaces: the chat composer (which is also the live dictation preview — partial results are written straight into it), the group-room composer, the clarification answer, message bubbles, the chat header title, session and room rows, the dictation-language chip and picker, room name/summary/member name, agent display name and description, workflow names and run inputs, Kanban title/description/reason/comment and cron job name/prompt.

Known gap: text fields inside a SwiftUI `.alert` (rename conversation, rename category, rename room) are bridged to `UIAlertController`, which ignores these modifiers; they still follow the interface. Moving those to sheets is the fix and has not been done.

Spacing is logical (leading/trailing) and directional icons mirror. Pure-logic coverage: `HermesStudioTests/ContentDirectionTests.swift`.

## Install on a personal iPhone

1. Open `HermesStudio.xcodeproj` in Xcode.
2. Select the `HermesStudio` target, open **Signing & Capabilities**, and choose your Apple ID's Personal Team.
3. Connect the iPhone, choose it as the run destination and press Run.
4. If iOS asks, enable Developer Mode and trust the developer profile in **Settings > General > VPN & Device Management**.

A free Personal Team installation normally needs to be signed again after seven days. TestFlight and App Store distribution require the paid Apple Developer Program.
