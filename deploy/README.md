# الانتقال من ستاك Hermes الحالي

هذا إعداد للسيرفر الذي أرسله المستخدم، وليس أمرًا لنشره تلقائيًا.
لا تشغّله إلى جانب الحاوية الحالية: كلاهما اسمه `hermes-main` ويستعمل البيانات نفسها.

## ما يتغير وما يبقى

تتغير صورة التطبيق إلى صورة النسخة الشخصية التي اجتازت الفحص. يبقى اسم الخدمة
والحاوية، رابط `hermes.i3u.us`، شبكة `proxy`، مسار `/webhooks/*` إلى المنفذ
`8644` وبقية الموقع إلى `6060`. لا نفتح منافذ مباشرة للإنترنت.
يبقى Hermes وStudio داخل حاوية واحدة، مع وحدتي التخزين الحاليتين.

أضفنا مجلد أوامر الوكلاء المحفوظ إلى بداية `PATH`؛ الستاك السابق يكتب `PATH`
يدويًا فيتجاوز القيمة الموجودة في الصورة. هذا لا ينقل أي تثبيت قديم تلقائيًا:
البرامج المثبتة داخل الطبقة المؤقتة قد تحتاج تنزيلًا واحدًا في المسار الدائم.
لا نربط ملفات النظام كلها بفوليوم، ولا نغيّر مسارات بيانات البروفايلات.

## قبل التبديل

1. على **سيرفرك** اعرض أسماء التخزين الفعلية دون طباعة البيئة أو المفاتيح:

```bash
docker inspect hermes-main --format '{{range .Mounts}}{{println .Type .Name .Source "->" .Destination}}{{end}}'
docker inspect hermes-main --format '{{.Image}}'
```

سجّل اسم الفوليوم المرتبط بـ `/home/agent/.hermes` والمرتبط بـ
`/home/agent/.hermes-web-ui`؛ قد يحملان بادئة اسم الستاك. إذا كان النوع `bind`
بدل `volume` فتوقف وعدّل القالب لمسارات الربط الفعلية. لا تخمّن الأسماء.

2. أوقف الخدمة مؤقتًا من مدير الستاك، وخذ نسخة احتياطية متسقة من **الوحدتين**
   وأنت محتفظ بالصورة القديمة والستاك السابق. نسخة ملفات SQLite أثناء الكتابة
   قد تكون غير متسقة. لا تستخدم `down -v` أو تحذف الفوليومات.
3. أضف قيم `server.env.example` إلى بيئة الستاك الحالي، مع أسماء الفوليومات
   الصحيحة ومرجع الصورة المختبرة. القالب يستعمل `external: true` عمدًا حتى
   يفشل عند عدم وجود البيانات المطلوبة بدل إنشاء بيانات فارغة بصمت.
4. المستودع والصورة الشخصية خاصّان. جهّز اعتماد قراءة `GHCR` في مدير الستاك أو
   `docker login ghcr.io` على السيرفر باستخدام رمز محدود بصلاحية قراءة الحزم.
   لا تضع الرمز في YAML أو Git أو المحادثة. العضوية في GitHub وحدها ليست تسجيل
   دخول إلى سجل الحاويات على سيرفرك.
5. تحقق من الصياغة في مكان الملف والبيئة المناسبة:

```bash
docker compose --env-file server.env -f compose.server.yml config --quiet
```

6. استبدل تعريف **الستاك الحالي** بالقالب، ثم حدّث الخدمة بالصورة الجديدة.
   لا تنشئ ستاكًا موازيًا يكتب في البيانات نفسها. إذا لم يدعم السيرفر `sysbox-runc`
   غيّر `STUDIO_RUNTIME` إلى `runc` كما في إعدادك السابق.

## فحص ما بعد الانتقال

تحقق من دخول حسابك السابق وظهور البروفايلات والمحادثات، ثم جرّب رسالة واحدة
وقناة تيليقرام وويب هوك تجريبيًا. جرّب إعادة إنشاء الحاوية وتأكد من بقاء البيانات
والبرامج التي ثبّتها Studio في المسار الدائم. اختباراتنا المعزولة لا تعوّض تجربة
مزوديك وشبكتك الحقيقية. لا ترسل مفاتيح أو بيانات إنتاج ضمن تقرير الأخطاء.

عند وجود مشكلة: أوقف الحاوية الجديدة، واستعد الصورة السابقة **مع نسخة البيانات
السابقة عند وجود ترحيلات**. إعادة الصورة وحدها لا تضمن التراجع عن قواعد البيانات.

## إصدار الصورة

تشغيل البناء الشخصي في GitHub يدوي ومخصص لهذا المستودع؛ لا ينشر إلى حساب المطور.
يشترط نجاح `Build` و`Playwright` وحارس الرخصة لنفس commit قبل البناء والنشر؛
إذا ما زالت الاختبارات تعمل فانتظرها قبل تشغيل مسار الصورة.
البناء الحالي يستهدف `linux/amd64` فقط؛ تحقق من معمارية سيرفرك بـ `uname -m`
قبل استخدامه. يحتاج سيرفر ARM صورة إضافية واختبارًا عليها، وليس مجرد تغيير الوسم.
صورة Hermes الأساسية مثبتة ببصمة في `Dockerfile` حتى لا تختلف فجأة بين بناءين؛
نحدّثها عمدًا مع اختبار التشغيل، ولا يعني ذلك تثبيت أحدث مكتبات النظام إلى الأبد.
الوسم `sha-<commit>` يربط الصورة بالكود. للضمان الأقوى ثبّت digest الناتج من البناء.
لا تستخدم `latest` متحركًا للتحديثات غير المراجعة، ولا تغيّر ستاك الإنتاج قبل
نجاح اختبارات الصورة والتحقق من إمكانية سحبها من سيرفرك.
