# تصميم وضع «مرتبط بالسيرفر» لتطبيق سطح المكتب

المسؤول: twuijri
الفرع: docs/desktop-server-mode-design
الحالة: review

## المشكلة والهدف
تطبيق Studio لسطح المكتب (`packages/desktop`) يشغّل Hermes والنماذج والأدوات
محلياً فقط، فلا فائدة من السيرفر لمستخدم التطبيق. المالك يريد وضعاً ثانياً اختيارياً:
التطبيق يتصل بـ Studio على سيرفره ويعتمد على Hermes وذاكرته ونماذجه هناك، مع
قدرة Hermes على رؤية جهاز المستخدم والعمل عليه عبر أدوات مساعدة صغيرة، دون كسر
الوضع المحلي لمن يحدّث التطبيق.

الدليل من الكود: الواجهة داخل التطبيق تتجاهل عنوان السيرفر المحفوظ (`getBaseUrl`
عند `isDesktopShell()`)، وبروتوكول أجهزة Studio الحالي (`lan-peer-socket.ts`) يسمح
للطرف المتصِل بالتحكم بالطرف المستقبِل فقط، فالاتصال الحالي من سطح المكتب إلى
السيرفر يعطي «رؤية السيرفر» لا العكس، كما لاحظ المالك.

## القرار والموافقات
المالك وافق (2026-09-18) على بدء التصميم أولاً بلا كود. النتيجة وثيقة
`docs/DESKTOP-SERVER-MODE.md`: وضعان (محلي كما هو، ومرتبط بالسيرفر)، «وكيل جهاز»
يتصل صادراً بالسيرفر ويعلن نفسه قابلاً للتحكم بعد اقتران يعتمده المالك، وأدوات
Hermes عبر مجموعة أدوات الأجهزة المُدارة الموجودة، وأربع مراحل تنفيذ. التنفيذ
يحتاج اعتماد المالك للوثيقة ثم يبدأ بالمرحلة الأولى كمهمة مستقلة.

## الملفات والتأثير

`docs/KNOWLEDGE-WORKFLOW.md`. لا تغيير في الكود.

## الفحوص
توثيق فقط: `npm run harness:check` و`npm run test:personal` و`git diff --check`
(النتائج في وصف طلب الدمج). لا بناء ولا اختبارات متصفح.

## المخاطر والرجوع
لا ينطبق على هذه المهمة (وثيقة). مخاطر التنفيذ مسجلة في الوثيقة (توافق العقد
للخلف، حساسية التحكم بالشاشة، توزيع التطبيق يدويًا).

## التسليم والخطوة التالية
مرفوع بطلب دمج توثيقي إلى `main`. الخطوة التالية: قراءة المالك للوثيقة واعتمادها
أو تعديلها، ثم فتح مهمة المرحلة الأولى (وضع الارتباط في التطبيق).
