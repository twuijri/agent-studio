# سجلات التغييرات والتسليم

كل مهمة لها ملف مستقل، لا ملف يوميات ضخم يكتب فيه الجميع. تسمية الملف:
`YYYY-MM-DD-owner-short-topic.md`، مثل `2026-09-15-twuijri-team-rules.md`.
استخدم اسم المسؤول البشري أو معرفه، لا اسم المساعد وحده. إذا تكررت التسمية أضف
لاحقة واضحة. الملف نفسه يُحدّث طوال المهمة؛ لا تنشئ سجلًا لكل رسالة أو تعديل صغير.

أنشئه قبل التنفيذ المحلي، وشارك المهمة والفرع في وسيلة تنسيق الفريق المصرح بها.
لا تفترض أن ملفًا لم يُرفع أصبح مرئيًا لباقي الفريق. عند فتح PR بإذن صاحبه،
ضمّن السجل في الفروق. إذا امتدت المهمة إلى PR مستقل جديد، أنشئ سجلًا جديدًا يربط بالسابق.

الحالات: `planned`، `in-progress`، `blocked`، `review`، `done`.
`done` تعني اكتمال نطاق المهمة المراجع، لا تعني تلقائيًا النشر على السيرفر؛
قسم التسليم يحدد ما تم فعليًا. لا تسمِّ عملًا غير مراجع `done`.

انسخ البنية التالية. حافظ على أسماء الأقسام ليتحقق منها CI، واستبدل التعليمات
بمعلومات حقيقية. إن لم ينطبق قسم، اذكر السبب بدل حذفه. لا تضع رموز وصول أو
بيانات خاصة أو سلسلة تفكير المساعد. اربط الأدلة والاختبارات بدل نسخ مخرجاتها كاملة.

```markdown
# عنوان المهمة

المسؤول: <human-owner>
الفرع: <topic-branch>
الحالة: planned

## المشكلة والهدف
الدليل، السلوك المطلوب، وخارج النطاق.

## القرار والموافقات
الحل وسببه والبدائل المهمة. ما الذي وافق عليه صاحب الطلب؟ وما الذي ينتظر إذنه؟

## الملفات والتأثير
المسارات أو الوحدات المتأثرة، والوثائق الأصلية التي جرى تحديثها.

## الفحوص
الأوامر المنفذة ونتائجها وبيئتها. ما لم يُنفذ وسببه، والفرق بين اختبار محلي وCI.

## المخاطر والرجوع
تأثير البيانات والتوافق، خطة الرجوع، أو سبب عدم انطباقها.

## التسليم والخطوة التالية
الحالة الفعلية، العائق إن وجد، روابط الفرع/PR/الإصدار عند وجودها، وخطوة المتابع.
```

الفحص `Change record` يطلب سجلًا جديدًا أو محدثًا بهذه البنية في PR؛ لا يفسر
محتواه أو يصدق على صحة الفحوص والموافقات. المراجعة البشرية مطلوبة.
هذا المجلد ليس سجل محادثات، ولا بديلًا عن تحديث وثائق التشغيل عند تغييرها.
