# الكانبان: قراءة مباشرة من قاعدة Hermes بدل عملية CLI لكل طلب

المسؤول: twuijri
الفرع: feat/kanban-direct-reads
الحالة: review

## المشكلة والهدف
على ستاك التجربة، فتح لوحة الكانبان يأخذ نصف دقيقة أو أكثر قبل ظهور المهام.
السبب في الكود الموروث: كل قراءة (اللوحات، القائمة، الإحصائيات، المكلَّفون،
تفاصيل المهمة، المرفقات) تُشغّل عملية Python كاملة لأمر `hermes kanban ...`،
وفتح الصفحة يطلق ست عمليات متزامنة (الإحصائيات وحدها تشغّل القائمة مرتين)، ثم
ثلاثاً كل 15 ثانية، وكل عملية تحمّل Python وHermes من الصفر.

بيانات الكانبان في الحقيقة قاعدة SQLite صغيرة لكل لوحة (`<root>/kanban.db`
للافتراضية، `<root>/kanban/boards/<slug>/kanban.db` لغيرها) يفتحها Hermes بوضع
WAL. المشروع يقرأ `state.db` مباشرة للقراءة فقط عبر `node:sqlite` لسجل
المحادثات، فالسابقة موجودة والصورة تعمل بـ Node 24.

خارج النطاق: أي كتابة مباشرة في قاعدة Hermes (كل التعديلات تبقى عبر CLI بحراسه)،
تغيير عقد API للواجهة، تشغيل Hermes كخدمة دائمة.

## القرار والموافقات
اعتمد صاحب المشروع بتاريخ 2026-09-17 «حلًا جذريًا حتى لو اختلف عن طريقة المطور
الأصلي»، ثم وافق على هذا التصميم بعد عرض المخاطر والبدائل:

- محوّل قراءة فقط `services/kanban/kanban-db.ts` يطابق مسارات Hermes وشكل مخرجات
  `--json` (القائمة، `show`، الإحصائيات، اللوحات مع `board.json` و`current`،
  المكلَّفون، المرفقات).
- الخدمة تجرّب القراءة المباشرة أولًا وترجع تلقائيًا إلى CLI عند أي فشل (ملف غير
  موجود، اختلاف مخطط، Node بلا `node:sqlite`) مع تحذير واحد في السجل؛ متغير
  `HERMES_WEB_UI_KANBAN_DIRECT_READS=0` يفرض مسار CLI للتشخيص.
- ذاكرة قصيرة (3 ثوانٍ) ودمج للطلبات المتطابقة المتزامنة `kanban-read-cache.ts`،
  تُبطَل للوحة عند أي أمر تعديل من الخادم وعند كل حدث يصل من `kanban watch`.
- البديل المرفوض: تشغيل Hermes كخدمة RPC دائمة؛ أكبر ويغيّر تشغيل الحاوية.

الدمج في `test` وبناء صورة `test` ضمن التفويض الدائم؛ الدمج في `main` قرار المالك.

## الملفات والتأثير
- جديد: `packages/server/src/modules/hermes/services/kanban/kanban-db.ts`،
  `kanban-read-cache.ts`، `tests/server/kanban-db.test.ts`.
- `kanban-service.ts`: القراءات عبر `readDirectOrCli` مع الاحتفاظ بدوال CLI كمسار
  رجوع؛ إبطال الذاكرة بعد كل تعديل و`createTask`.
- `sockets/kanban-events.ts`: إبطال الذاكرة عند أحداث Hermes.
- لا تغيير في المتحكم أو المسارات أو العميل.

فرق مقصود عن CLI: `stats.by_assignee` يعدّ المهام بلا مكلَّف تحت `default` كما
يفعل الخادم للمؤرشف أصلًا، ويشمل المؤرشف كما كان الخادم يضيفه.

## المخاطر والرجوع
- ارتباط بمخطط جداول Hermes: يُعالج بالرجوع التلقائي إلى CLI واختبار على قاعدة
  مبنية من تعريفات جداول Hermes نفسها. تحديث Hermes الذي يغيّر الأعمدة المقروءة
  يُظهر تحذيرًا في السجل ويعود للمسار البطيء لا إلى كسر.
- القراءة المتزامنة مع كتابة الوكيل: WAL يسمح بها، والاتصال للقراءة فقط مع
  `busy_timeout`.
- الذاكرة قد تُظهر حالة أقدم بثلاث ثوانٍ فقط إذا تغيّر شيء من خارج الخادم وبلا
  حدث من `watch`؛ الاستفتاء كل 15 ثانية يصحّحها.
- الرجوع: إرجاع الكود أو ضبط `HERMES_WEB_UI_KANBAN_DIRECT_READS=0`.
